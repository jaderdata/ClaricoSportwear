# PHASE 3 — Build the Central Product Management & Publishing Control Panel

## Project Context

Phase 1 and Phase 2 have already established the foundation of this project.

### Phase 1 — Depop Extraction

My existing Depop listings were extracted and organized into migration files containing product information, marketplace metadata, and images.

### Phase 2 — Database Evolution

My existing website and existing Supabase database were analyzed and evolved without rebuilding the project from scratch.

Supabase is now being established as the **Single Source of Truth** for product information.

The architecture is moving toward:

**Admin Panel → Supabase → Website / Marketplaces**

Now we need to build the interface that I will actually use to manage this system.

---

# Main Objective

Build a private **Product Management & Publishing Control Panel** inside my existing website/application.

From this point forward, I should NOT need to create a product manually inside Depop first.

Instead, the workflow should become:

**Create Product → Save to Supabase → Select Sales Channels → Publish Later**

The administrative panel becomes the place where products originate.

Supabase remains the actual source of truth.

The admin panel is simply the interface I use to manage that data.

---

# IMPORTANT ARCHITECTURAL PRINCIPLE

Do NOT create a separate application unless there is a strong technical reason.

The admin panel should preferably be integrated into my existing website/project.

Reuse:

* existing framework
* existing Supabase connection
* existing authentication
* existing components
* existing design system
* existing database types
* existing storage architecture
* existing utilities

Do not duplicate infrastructure that already exists.

---

Create a private administrative area inside the existing application.

# STEP 9 — Product Status

Every product should have a clear internal lifecycle.

Use the status architecture created during Phase 2.

Conceptually, statuses may include:

* Draft
* Ready
* Active
* Archived

For example:

### Draft

Product is incomplete.

### Ready

Product information is complete and ready for distribution.

### Active

Product is available through at least one sales channel.

### Archived

Product should no longer be actively sold.

Adapt these statuses to the existing schema instead of creating duplicate concepts.

---

# STEP 10 — Sales Channel Selection

This is one of the most important parts of Phase 3.

When creating or editing a product, I should be able to indicate where I eventually want the product published.

For example:

**Sales Channels**

☑ Website

☑ Depop

☐ Vinted

☐ eBay

The exact interface may use checkboxes, toggles, or another appropriate UI.

IMPORTANT:

Selecting a marketplace during Phase 3 should NOT automatically launch browser automation or publish the listing.

At this stage, it should simply store my publishing intent in Supabase.

For example:

`Website → Selected`

`Depop → Selected`

`Vinted → Selected`

`eBay → Not Selected`

The automation engine will process these selections in a later phase.

---

# STEP 11 — Separate Intent From Actual Marketplace Status

Do not confuse:

**Where I WANT the product published**

with:

**Where the product IS currently published**

These must be separate concepts.

Example:

Product 123

Desired Channels:

Website → YES

Depop → YES

Vinted → YES

eBay → NO

Actual Status:

Website → Active

Depop → Active

Vinted → Not Published

eBay → Not Published

This distinction will be extremely important once automation begins.

# STEP 13 — Prevent Duplicate Marketplace Listings

Existing migrated Depop products must be treated carefully.

If a product already has:

* a Depop listing ID
* a Depop listing URL
* marketplace status = published

the system must understand that the listing already exists.

Do NOT create a new Depop listing for that product later without explicit instruction.

This principle must be preserved in the data model and UI.

# STEP 15 — Duplicate Product

Add a **Duplicate Product** function if it fits naturally into the existing architecture.

This could save significant time when creating similar products.

For example:

Product A:

`Funny BJJ Black Belt Shirt`

Product B:

`Funny BJJ Purple Belt Shirt`

The duplicate should receive a new internal product ID.

It must NOT inherit external marketplace listing IDs.

Never duplicate:

* Depop listing ID
* Vinted listing ID
* eBay listing ID
* marketplace URLs

Marketplace identity must remain unique.

# STEP 21 — Speed Is Important

The admin interface should optimize for fast product creation.

I do not want to spend several minutes manually entering every product.

Design the workflow to minimize clicks and repetitive work.

Where appropriate:

* Remember sensible defaults
* Reuse previous values
* Make tags easy to add
* Make image upload fast
* Make variants easy to duplicate
* Avoid unnecessary confirmation dialogs

However, do not sacrifice data integrity for speed.

Work in this order:

1. Inspect the current application after Phase 2.
2. Inspect the final Supabase schema.
3. Identify existing components that can be reused.
4. Design the admin panel architecture.
5. Design the product creation workflow.
6. Design the product editing workflow.
7. Design marketplace selection/status UI.
8. Explain the proposed implementation.
9. Identify any required database changes.
10. Identify risks or breaking changes.
11. **STOP and show me the plan before implementing major changes.**
12. After my approval, implement the admin area.
13. Test existing migrated products.
14. Test creation of a new product.
15. Verify Supabase data.
16. Verify the existing website still works.
17. Document the implementation.

---

# Definition of Done

Phase 3 is complete when:

* I have a private admin panel.
* I can see my existing products.
* I can search and filter products.
* I can create a new product.
* I can upload and manage product images.
* I can edit existing products.
* I can manage tags/categories/variants.
* I can select desired sales channels.
* I can distinguish desired channels from actual publication status.
* Existing Depop listings remain correctly linked.
* New products are stored in Supabase.
* The existing website continues working.
* No marketplace automation occurs yet.

The fundamental change after Phase 3 should be:

**I no longer need to create a product on Depop first.**

From this point forward:

**I create the product once in my own system, Supabase stores the canonical product, and future phases will distribute that product to whichever marketplaces I select.**
