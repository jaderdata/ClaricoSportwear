# PHASE 5 — Marketplace Synchronization, Reconciliation & Product Lifecycle Engine

## Project Context

Phases 1 through 4 have established the core architecture.

### Phase 1 — Existing Marketplace Migration

Existing Depop listings were extracted and migrated into the new centralized architecture.

### Phase 2 — Supabase as the Central Database

The existing website database was evolved so that Supabase became the central source of product information.

### Phase 3 — Product Management Control Panel

A private admin panel was created where products can be:

* Created
* Edited
* Organized
* Assigned to sales channels
* Managed without depending on an external marketplace

### Phase 4 — Marketplace Publishing Engine

The system can publish products from Supabase to selected marketplaces.

The architecture now conceptually works as:

**Admin Panel**

↓

**Supabase**

↓

**Publishing Engine**

↓

**Website / Depop / Vinted / eBay**

↓

**External Listing IDs + URLs + Status**

↓

**Supabase**

Phase 5 will make this architecture continuously maintainable.

---

# MAIN OBJECTIVE

Build the synchronization and reconciliation layer that keeps product information and marketplace listing states aligned over time.

Phase 4 answers:

> "How do I publish this product?"

Phase 5 answers:

> "Now that this product exists in multiple places, how do I keep everything organized and synchronized?"

The system must be able to detect changes, determine what needs to be synchronized, safely execute those changes, verify the result, and record the final state.

---

# MOST IMPORTANT ARCHITECTURAL RULE

Supabase remains the:

# SINGLE SOURCE OF TRUTH

The default direction of synchronization should be:

**Supabase → Marketplaces**

NOT:

**Marketplace ↔ Marketplace**

and NOT unrestricted:

**Marketplace → Supabase**

For example:

If Supabase says:

Price = `$24.99`

and Depop says:

Price = `$22.99`

the system should NOT automatically assume Depop is correct.

The system should detect the difference and follow the synchronization policy defined in Supabase.

This prevents external marketplaces from silently overwriting canonical product information.

# STEP 2 — Define Canonical Fields

Determine which fields are controlled by Supabase.

Examples may include:

* Canonical title
* Canonical description
* Canonical images
* Base price
* Product category
* Tags
* Variants
* Sizes
* Colors
* Product status
* Availability

Marketplace-specific overrides may still exist.

For example:

Canonical price:

`$24.99`

Depop price override:

`$26.00`

Vinted price override:

`$25.00`

eBay price override:

`$27.99`

In this case, synchronization should respect the marketplace-specific override.

Do not overwrite valid marketplace overrides with canonical values.

# STEP 3 — Track Product Versions

This may use:

* `updated_at`
* revision numbers
* content hashes
* version numbers
* field-level timestamps

The system should be able to answer:

`18`

`16`

# STEP 5 — Field-Level Synchronization

Do not blindly republish the entire listing every time one field changes.

Where supported, determine what changed.

For example:

Previous:

Price → `$24.99`

New:

Price → `$22.99`

Only price changed.

The synchronization system should preferably create:

`UPDATE_PRICE`

rather than rebuilding the entire listing.

Other possible operations:

`UPDATE_TITLE`

`UPDATE_DESCRIPTION`

`UPDATE_IMAGES`

`UPDATE_PRICE`

`UPDATE_VARIANTS`

`UPDATE_AVAILABILITY`

`UPDATE_CATEGORY`

`UPDATE_FULL_LISTING`

The exact operations depend on marketplace capabilities.

# STEP 7 — Change Detection

When a canonical product changes, determine which marketplaces are affected.

Example:

Product A is published on:

Website → YES

Depop → YES

Vinted → YES

eBay → NO

Price changes.

Expected behavior:

Website → Update

Depop → Update

Vinted → Update

eBay → NOTHING

The system must never create synchronization jobs for marketplaces where the product is not published or selected.

---

# STEP 8 — Marketplace-Specific Overrides

Marketplace overrides must take precedence over canonical values for that marketplace.

Example:

Canonical price:

`$24.99`

Depop override:

`$26.99`

Vinted:

No override

After canonical price changes to:

`$22.99`

Expected result:

Depop → remains `$26.99`

Vinted → changes to `$22.99`

Website → changes according to website pricing policy

This prevents synchronization from destroying intentional channel-specific strategies.

# STEP 9 — Synchronization Jobs

Extend the Phase 4 job queue.

Possible actions now include:

`publish`

`update`

`verify`

`pause`

`end_listing`

`refresh_status`

Do not create an entirely separate queue unless there is a strong architectural reason.

Use the existing job infrastructure.

---

# STEP 10 — Synchronization Workflow

A typical update job should execute:

1. Receive synchronization job.
2. Lock job.
3. Load canonical product.
4. Load marketplace listing record.
5. Confirm marketplace is still authorized.
6. Confirm external listing exists.
7. Load marketplace overrides.
8. Determine effective marketplace values.
9. Compare with last known marketplace state.
10. Determine required changes.
11. Execute connector update.
12. Verify the marketplace accepted the change.
13. Read back marketplace state where supported.
14. Update synchronization metadata.
15. Mark job completed.
16. Record audit event.

---

# STEP 11 — Never Assume an Update Succeeded

Clicking "Save" or receiving a browser action result is not sufficient.

Verify the resulting listing state whenever technically possible.

Example:

Requested:

Price → `$22.99`

After update:

Read marketplace listing.

Expected:

Price → `$22.99`

If actual value remains:

`$24.99`

mark the synchronization as failed or inconsistent.

Do not mark it successful simply because the submission action completed.

---

# STEP 12 — Reconciliation

Synchronization is proactive.

Reconciliation is defensive.

Create a process that periodically checks whether Supabase and marketplace states still agree.

For example:

Supabase expected:

Vinted price → `$24.99`

Marketplace observed:

Vinted price → `$22.99`

Result:

`DRIFT DETECTED`

The system should record the discrepancy.

---

# STEP 13 — Drift Detection

Possible drift examples:

* Price differs
* Title differs
* Description differs
* Listing disappeared
* Listing was manually ended
* Marketplace status changed
* Images differ
* Availability differs

Do not automatically correct every type of drift.

Classify drift first.

---

# STEP 14 — Drift Policies

Create configurable behavior.

Possible policies:

### AUTO_CORRECT

Automatically restore the Supabase value.

### REPORT_ONLY

Show the discrepancy but do nothing.

### REQUIRE_APPROVAL

Ask for approval before changing the marketplace.

Different fields may use different policies.

Example:

Price:

`AUTO_CORRECT`

Title:

`REQUIRE_APPROVAL`

Listing manually deleted:

`REPORT_ONLY`

This gives us control over automation risk.

---

# STEP 15 — Manual Marketplace Changes

Users may occasionally edit listings directly inside Depop, Vinted, or eBay.

The system should detect this when possible.

Do NOT automatically import those changes into canonical Supabase data.

Instead show something like:

`Marketplace change detected`

Example:

Depop title:

`New title`

Supabase title:

`Original title`

Available actions may eventually include:

`Restore Supabase version`

or:

`Accept marketplace version`

The default should remain:

**Supabase is authoritative.**

---

# STEP 16 — Controlled Import From Marketplace

Although Supabase is authoritative, provide a future-safe mechanism for intentionally accepting a marketplace value.

Example:

I manually improve a title on Depop.

The system detects it.

I choose:

`Accept Depop title as canonical`

Only after explicit approval should that external value update the canonical product.

Never silently overwrite canonical product data.

---

# STEP 17 — Price Synchronization

Price synchronization deserves dedicated logic.

Support:

* Canonical base price
* Marketplace price overrides
* Marketplace fees
* Future pricing rules

Example:

Base price:

`$24.99`

Depop:

`$24.99`

Vinted:

`$23.99`

eBay:

`$27.99`

These should all be legitimate states.

Do not assume every marketplace must have the same price.

# STEP 18 — Availability Synchronization

Track whether a product is:

* Available
* Temporarily unavailable
* Archived
* Sold out
* Disabled

If a canonical product becomes unavailable, determine the appropriate action for each marketplace.

Do not automatically delete marketplace listings unless the configured policy explicitly requires it.

Prefer reversible actions where marketplaces support them.

# STEP 19 — Inventory Architecture

Prepare the architecture for inventory synchronization.

Even if many current products are made-to-order, the system should support future inventory quantities.

Potential fields:

`inventory_quantity`

`reserved_quantity`

`available_quantity`

`inventory_policy`

Possible policies:

`UNLIMITED`

`MADE_TO_ORDER`

`TRACK_QUANTITY`

This prevents the architecture from assuming every product has identical inventory behavior.

---

# STEP 20 — Sold Product Handling

If a marketplace reports that an item was sold, record the event.

Do NOT immediately assume the canonical product should disappear everywhere.

The correct action depends on inventory policy.

Example:

Made-to-order shirt:

Sale on Depop

Result:

Product remains available elsewhere.

Unique item:

Sale on Depop

Result:

Product may need to become unavailable on Vinted/eBay.

Therefore, sales and inventory behavior must depend on product configuration.

Support marketplace listing lifecycle states.

Conceptually:

`publishing`

`active`

`update_pending`

`paused`

`sold`

`ended`

`removed`

# STEP 22 — External Listing Health Checks

Create lightweight verification of marketplace listings.

The system should eventually know whether an expected listing still exists.

Example:

Supabase:

Depop → Published

Marketplace:

Listing no longer exists

Result:

`LISTING MISSING`

Do not automatically republish immediately.

Record the discrepancy first.

This protects against creating a listing that the marketplace removed intentionally.

---

# STEP 23 — Marketplace Removal Detection

If a marketplace removes or restricts a listing:

Do not automatically fight the marketplace by continuously recreating it.

Mark:

`MARKETPLACE_REMOVED`

or equivalent.

Record any available reason.

Require manual review before republishing.

---

# STEP 24 — Synchronization Frequency

Do not synchronize everything continuously without reason.

Use event-driven synchronization where possible.

Example:

Product edited

↓

Determine affected marketplaces

↓

Create update jobs

Periodic reconciliation can run less frequently.

This reduces:

* unnecessary requests
* marketplace load
* automation risk
* cost
* rate-limit problems

---

# STEP 25 — Rate Limiting

Each marketplace connector must respect appropriate request and action rates.

Implement:

* queue throttling
* concurrency limits
* exponential backoff where appropriate
* marketplace-specific limits

Do not create aggressive automation behavior.

---

# STEP 26 — Retry Safety

Update jobs must remain idempotent where possible.

If:

`UPDATE_PRICE → $24.99`

fails halfway through, retrying should not produce unintended behavior.

Before retry:

1. Check current marketplace state.
2. Determine whether the previous attempt actually succeeded.
3. Only execute the missing action.

---

# STEP 27 — Conflict Detection

Detect situations where multiple changes happen simultaneously.

Example:

Supabase price changes.

Before synchronization runs, price changes again.

Do not publish the outdated intermediate value unnecessarily.

Prefer the newest valid canonical state.

The job system should detect stale jobs.

---

# STEP 28 — Stale Job Protection

Example:

Job A created:

Price → `$24.99`

Before Job A runs:

Canonical price changes to `$22.99`

Job A should not overwrite the marketplace with an outdated value.

Before execution, always reload the latest canonical product state.

---

# STEP 29 — Product Deactivation

If a product is archived in Supabase, determine what should happen to external listings.

Possible policy:

Website → Hide

Depop → Pause/end

Vinted → Pause/end

eBay → End listing

However, this must be policy-driven.

Do not automatically remove listings without explicit configuration.

---

# STEP 30 — Channel Deselection

If I deselect a marketplace:

Example:

Vinted:

Desired → NO

Actual → Published

Do not automatically delete the listing.

Instead create a state such as:

`ACTION REQUIRED`

Possible options:

`Leave Listing Active`

`Pause Listing`

`End Listing`

This protects against accidental destructive actions.

# STEP 38 — Human Approval for Risky Actions

Certain operations should require explicit approval.

Examples:

* Ending listings
* Deleting listings
* Replacing all images
* Accepting marketplace data as canonical
* Republishing marketplace-removed listings
* Large bulk price changes

Do not optimize away important human control.

---

# STEP 39 — Website Synchronization

The website should remain the easiest channel because it reads from Supabase directly.

Changes to canonical product data should appear according to the existing website architecture.

Do not create unnecessary browser automation for the website.

If caching exists, ensure updates properly invalidate or refresh relevant cached data.

---

# STEP 40 — Marketplace Polling

Only poll marketplaces where necessary and supported.

Prefer:

* APIs
* webhooks
* official events
* supported marketplace integrations

over constant browser scraping.

If browser-based verification is necessary, keep it conservative.

Do not bypass marketplace security or anti-bot mechanisms.

---

# STEP 41 — Two-Way Data Is NOT the Default

Even after Phase 5, do not create uncontrolled two-way synchronization.

The architecture should remain:

**Supabase → Marketplace**

with:

**Marketplace → Observation / Status / Sales Events**

External marketplace data may inform Supabase.

It should not automatically rewrite canonical product data unless explicitly authorized.

# DEFINITION OF DONE

Phase 5 is complete when:

* Supabase remains the canonical product source.
* Product changes can generate marketplace update jobs.
* Only relevant marketplaces receive updates.
* Marketplace-specific overrides are preserved.
* Changes are verified after synchronization.
* Drift can be detected.
* Marketplace listing health can be checked.
* Failed synchronization is visible.
* Retry behavior is safe.
* Stale jobs cannot overwrite newer product data.
* Authentication problems pause affected operations.
* Marketplace removal is handled safely.
* Channel deselection does not automatically delete listings.
* Inventory architecture is prepared.
* Product lifecycle states are tracked.
* The admin panel clearly shows synchronization status.
* Synchronization history is auditable.

# CORE PRINCIPLE

Phase 4 answers:

**"Where should this product be published?"**

Phase 5 answers:

**"Now that it is published, is every selected channel still in the correct state?"**

Supabase remains authoritative.

Marketplaces are distribution channels.

The system should detect differences, synchronize intentionally, verify results, and ask for human approval when an action is ambiguous or destructive.

The final objective is:

**Create once. Manage once. Update once. Distribute everywhere I explicitly choose.**
