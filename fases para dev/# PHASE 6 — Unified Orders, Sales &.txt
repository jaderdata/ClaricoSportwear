# PHASE 6 — Unified Orders, Sales & Inventory Management

## Project Context

Phases 1 through 5 have established the core commerce infrastructure.

### Phase 1 — Existing Catalog Migration

Existing Depop listings were extracted and migrated into the centralized architecture.

### Phase 2 — Central Product Database

The existing Supabase database was evolved into the central product source of truth.

### Phase 3 — Admin Product Management

A private admin panel was created for managing products, images, variants, metadata, and desired sales channels.

### Phase 4 — Multi-Marketplace Publishing

Products can be published from Supabase to explicitly selected marketplaces.

### Phase 5 — Synchronization & Reconciliation

Published listings can be monitored, updated, reconciled, and compared against the canonical Supabase product state.

The architecture currently handles the **outbound product flow**:

**Supabase → Marketplaces**

Phase 6 must implement the opposite operational flow:

**Marketplaces → Orders → Supabase**

The objective is to create one centralized place where I can understand what was sold, where it was sold, what needs to be fulfilled, and how the sale affects product availability.

---

# MAIN OBJECTIVE

Build a unified **Order, Sales, Fulfillment & Inventory Management System** inside the existing application.

Orders may originate from:

* My website
* Depop
* Vinted
* eBay
* Future marketplaces

Regardless of where the customer purchased the product, the order should eventually be represented in Supabase using a normalized internal order structure.

The admin panel should become the central operational dashboard.

I should eventually be able to answer:

* What sold?
* Where did it sell?
* When did it sell?
* How much did it sell for?
* Which product was sold?
* Which variant was sold?
* Has it been paid?
* Does it need production?
* Does it need shipping?
* Has it shipped?
* What is the tracking number?
* Was it delivered?
* Was it cancelled?
* Was it refunded?
* How did this sale affect inventory?

---

Marketplace orders must NOT become the canonical product database.

Supabase remains the central system.

External marketplace orders are imported and normalized into internal Supabase records.

Conceptually:

**Website Order**

or

**Depop Order**

or

**Vinted Order**

**Marketplace Order Adapter**

**Normalized Internal Order**

The rest of the internal system should not need to understand every marketplace's raw order format.

# STEP 2 — Create a Canonical Internal Order Model

Create or evolve a normalized internal order model.

Potential entities may include:

`orders`

`order_items`

`order_events`

`order_payments`

`order_shipments`

`order_addresses`

`marketplace_orders`

`inventory_movements`

However, these names are conceptual.

Reuse existing tables if equivalent structures already exist.

An internal order should have its own canonical internal ID.

Example:

`order_id = UUID`

The marketplace order ID must remain an external identifier.

Do NOT use a Depop, Vinted, or eBay order ID as the primary internal order identity.

# STEP 3 — Separate Internal Order Identity From Marketplace Identity

Example:

Internal Order ID:

`a8f2...`

Marketplace:

`depop`

`DEPOP-123456`

`987654`

This allows the system to normalize orders regardless of origin.

Future marketplace integrations should not require redesigning the core order tables.

# STEP 4 — Marketplace Order Adapters

Each marketplace connector should have an order adapter.

Conceptually:

`Depop Order Adapter`

`Vinted Order Adapter`

`eBay Order Adapter`

Each adapter receives marketplace-specific order information and transforms it into the canonical internal order structure.

The internal order system should not contain large amounts of marketplace-specific branching logic.

Marketplace-specific behavior belongs in adapters/connectors.

# STEP 7 — Prevent Duplicate Orders

Order import must be idempotent.

Use a uniqueness concept such as:

`marketplace + external_order_id`

Before importing an order, check whether it already exists.

Example:

Marketplace:

`depop`

External Order:

`123456`

If already imported:

DO NOT create another internal order.

Instead determine whether the existing order needs updating.

# STEP 9 — Product Matching

Every imported marketplace order item should be matched to the canonical Supabase product whenever possible.

Preferred matching chain:

2. Marketplace listing record

4. Internal variant ID

Once matched, preserve that relationship for future operations.

# STEP 13 — Made-to-Order Products

The system must support made-to-order products.

This is especially important for printed apparel.

A marketplace sale may create a production requirement rather than simply decrementing finished-goods inventory.

Support an inventory/fulfillment policy such as:

`MADE_TO_ORDER`

For a made-to-order product:

Sale occurs

↓

Order imported

↓

Production task required

↓

Product produced

↓

Ready to ship

↓

Shipment created

This must be different from a unique physical item.

---

# STEP 14 — Inventory Policies

Support multiple inventory strategies.

Conceptually:

### UNLIMITED

No inventory tracking.

### MADE_TO_ORDER

Product is produced after sale.

### TRACK_QUANTITY

Physical stock quantity is tracked.

### UNIQUE_ITEM

Only one sellable unit exists.

These policies should affect what happens when a sale occurs.

---

# STEP 15 — Inventory Movements

Do not simply overwrite inventory numbers without history.

Create an inventory movement architecture.

Examples:

`+10 RESTOCK`

`-1 SALE`

`+1 RETURN`

`-1 DAMAGE`

`-1 MANUAL_ADJUSTMENT`

Every inventory change should be traceable.

Conceptually:

Current inventory = sum of valid inventory movements.

This creates a reliable audit trail.

---

# STEP 16 — Multi-Channel Inventory

If a physical inventory quantity is shared across marketplaces, all marketplaces must eventually reflect the same available quantity.

Example:

Internal inventory:

`1`

Product exists on:

Website

Depop

Vinted

eBay

Sale occurs on Vinted.

Internal available inventory becomes:

`0`

The system should then determine the appropriate action for:

Website

Depop

eBay

to prevent another sale.

This is critical for unique or limited-stock items.

---

# STEP 17 — Overselling Protection

Design inventory operations to avoid race conditions.

Example:

Inventory = `1`

Depop order arrives.

At nearly the same time:

Website order arrives.

The database must not independently allow both transactions to consume the same final unit.

Use database transactions, locking, atomic updates, or equivalent safe mechanisms.

Overselling protection should happen at the database level where possible.

---

# STEP 18 — Inventory Reservations

Prepare for inventory reservations.

Example:

Customer begins checkout on the website.

Inventory may temporarily become:

On hand: `5`

Reserved: `1`

Available: `4`

After successful payment:

Reserved: `0`

Sold: `1`

If checkout expires:

Reservation is released.

Do not overbuild this if the website checkout does not currently require it, but design the inventory model so it can support it.

**"What products do I sell, where should they be published, and are those listings synchronized?"**

The final objective is:

**One product system.**

**Multiple sales channels.**

**One order center.**
